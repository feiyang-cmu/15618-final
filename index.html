Parallelizing Data-Dependent Irregular Scatter on GPU: Token Routing in Mixture-of-Experts Models

Team: [Your Name] and [Partner Name]
Course: 15-618 Parallel Computer Architecture and Programming, Spring 2026

Summary

Mixture-of-Experts (MoE) models require routing thousands of tokens to a dynamically-selected subset of expert networks, which reduces to an irregular scatter whose write pattern is determined entirely at runtime. A sequential implementation is straightforward, but parallelizing it is hard: concurrent threads contend for write positions, the scatter destroys memory coalescing, and workload skew across experts creates load imbalance. We develop multiple parallel strategies in CUDA C++ that exploit the problem's structure — small key space, known after a cheap classification step — to resolve these challenges, targeting 10–20× speedup over a sequential baseline and near-peak HBM bandwidth utilization on NVIDIA GPUs.

Background

Modern MoE language models (Mixtral, DeepSeek-V3) contain E expert sub-networks per layer but activate only K of them per token. Given T input tokens, a small router network produces a (token_id, expert_id) assignment for each of the T×K activated slots. Before expert computation can proceed, all tokens must be packed into a contiguous buffer grouped by expert: all tokens assigned to Expert 0 first, then Expert 1, etc.

Concretely, the problem is: given T×K (token_id, expert_id) pairs where expert_id is determined at runtime, and a T×d embedding matrix, produce a (T×K)×d output buffer where entries are grouped by expert_id, plus metadata recording the permutation. A sequential implementation simply iterates over all T×K pairs, maintains a per-expert write pointer, and copies each token's d-dimensional embedding to the next available slot. This is O(T×K×d) — trivially correct but completely serial.

The Challenge

Write conflicts (the core difficulty): If we assign each of the T×K entries to a separate thread, multiple threads targeting the same expert must coordinate to obtain unique, non-overlapping write positions. Without coordination, two threads both writing to "Expert 0, next slot" would corrupt data. The conflict pattern is unknown until the router runs and changes every forward pass — fundamentally different from a regular scatter where the destination is a known function of the source index.

Memory coalescing vs. conflict freedom: On GPU, adjacent threads in a warp should write to adjacent memory addresses for coalescing. But after routing, adjacent threads likely target different experts (different memory regions), destroying coalescing. Restoring coalescing requires reordering threads, which itself requires synchronization. There is an inherent tension: any reordering step that improves memory access regularity adds synchronization cost.

Load imbalance: Expert popularity is not perfectly uniform. If we partition work by expert (one thread block per expert), blocks handling popular experts do more work while others sit idle. If we partition by token (ignoring expert assignment), we get good balance but worse locality. The optimal partitioning depends on the actual routing distribution, which varies at runtime.

Synchronization granularity trade-off: Eliminating write conflicts via global sort (radix sort on expert_id) requires multiple passes over the entire data with full HBM round-trips per pass. Eliminating them via per-thread atomics is single-pass but creates contention proportional to expert popularity. Between these extremes lies warp-cooperative coordination using SIMD intrinsics (__ballot_sync, __popc) — but this requires careful shared memory orchestration with bank-conflict avoidance. Each approach sits at a different point on the parallelism-vs-synchronization spectrum, and the best choice depends on workload parameters (E, K, T, skew).

Large payload per entry: Each scatter entry carries a d=4096 dimensional embedding (8 KB in bf16). Even a small amount of redundant data movement costs tens of MB of HBM bandwidth. The problem is memory-bound, not compute-bound — the challenge is minimizing total data movement while maintaining parallel correctness.

Goals and Deliverables

Plan to achieve (75%)

1. Sequential + naive parallel baselines: Single-threaded CPU reference implementation and a naive GPU parallelization using CUB RadixSort + separate gather kernel.

2. Three parallel GPU strategies:

  • Strategy A — Sort-first: Global radix sort on expert_id, then embarrassingly parallel gather. Multi-pass, conflict-free, bandwidth-heavy.
  • Strategy B — Atomic scatter: Per-thread atomicAdd on per-expert counters for write positions, then direct scatter. Single-pass, maximum contention.
  • Strategy C — Warp-cooperative scan: __ballot_sync to count per-expert tokens within each warp, block-level prefix scan for offsets, then conflict-free scatter. Single-pass, SIMD-coordinated.

3. Detailed performance analysis:

  • Speedup vs. sequential baseline: target 10–20×
  • Strategy comparison across parameter sweep: E ∈ {8, 16, 64, 128, 256}, K ∈ {1, 2, 8}, T ∈ {1K, 4K, 16K, 64K}
  • NCU microarchitectural analysis: HBM traffic, SMEM bank conflicts, atomic contention, achieved bandwidth vs. roofline
  • Crossover analysis: at which (E, skew) does each strategy win, and why

4. End-to-end MoE layer benchmark: Full pipeline — routing + packing + expert GEMM (cuBLAS) — measuring total layer time with each strategy.

Quantitative targets: Best strategy achieves ≥70% of peak HBM bandwidth; 10–20× over sequential; 2–4× over naive CUB RadixSort baseline for E ≤ 64.

Hope to achieve
  • CPU parallel implementation (OpenMP + SIMD) with cross-platform bottleneck comparison (false sharing vs. SMEM atomics)
  • Multi-GPU extension with NCCL AllToAllv + CUDA stream pipeline overlap (if multi-GPU hardware available)
  • Fused single-kernel routing: gate + softmax + topK + packing in one launch, eliminating all intermediate HBM materialization
If things go slowly
  • Drop Strategy C and focus on A vs. B comparison
  • Drop end-to-end MoE layer benchmark, focus on isolated scatter kernel analysis
  • Reduce parameter sweep to fewer configurations

Platform Choice

NVIDIA GPU is the natural platform for this workload: MoE inference runs on GPU, and the problem exercises GPU-specific parallel challenges — warp-level SIMD coordination (__ballot_sync), shared memory bank conflicts, memory coalescing sensitivity, and atomic contention scaling. CUDA C++ (rather than higher-level frameworks) gives explicit control over these mechanisms, which is essential for both implementing Strategy C and understanding performance through profiling. The problem is memory-bandwidth-bound, and modern GPUs offer 1–3 TB/s HBM bandwidth — the platform where scatter performance matters most.
