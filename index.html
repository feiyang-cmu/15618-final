Summary

Mixture of Experts models need to send tokens to dynamically selected experts before they can do any actual math. This routing process involves an unpredictable scatter step where tokens are packed into continuous memory based on their assigned expert, followed by an all to all communication phase across different GPUs if the model is distributed. Both of these steps are famously tricky to run in parallel because of runtime write conflicts, chaotic memory access patterns, and uneven workload distribution. We want to test and compare several different parallel implementation strategies to speed up this entire dispatch pipeline on NVIDIA GPUs. Our ultimate goal is to significantly beat simple baselines by smartly handling thread synchronization, memory layout, and overlapping communication with compute overhead.

Background

In a typical MoE layer, a router network looks at the input tokens and assigns each of them to a subset of available experts. Before the experts can start crunching numbers, we have to physically move the token embeddings into the correct memory locations for their assigned experts. If the experts are split across several GPUs, we also have to execute a network communication step to send the tokens over to the right machines. Once the experts finish their logic, we gather everything in reverse to put the results back together.

Writing a sequential version of this is pretty trivial: you just loop through the routing decisions and copy the embeddings one at a time. But doing it that way is way too slow for real models. The real puzzle is figuring out how to make this fast on GPUs, where you have thousands of threads tripping over each other, accessing memory in completely random ways, and waiting on expensive network transfers.

The Challenge

Write conflicts: When thousands of threads are packing tokens at the exact same time, threads that happen to target the same expert will inevitably fight to write to the exact same memory addresses. Since the router changes its mind on every forward pass, we cannot rely on any predetermined writing schedule.

Irregular memory access: After the routing step, neighboring threads usually need to send data to completely different experts, which means they write to memory locations that are far away from each other. This breaks GPU memory coalescing and basically tanks memory bandwidth. Trying to organize the data first, like grouping things by sorting, adds expensive synchronization barriers and extra data movement. Finding the right balance between clean memory access and low coordination overhead is tough.

Handling load imbalance: Some experts naturally get more tokens than others depending on the input text. Whatever method we use to divide up the parallel work needs to handle this uneven distribution on the fly so we never end up with idle GPU cores just waiting around.

Sending data across GPUs: Moving tokens around in a distributed cluster is messy because each GPU sends a random amount of data to every other GPU. If we run this normally, the GPU just sits there doing nothing while it waits for the data transfer to finish. To get acceptable performance, we need to hide this delay by pipelining the work and overlapping it with actual computation.

Choosing the right synchronization level: There are fundamentally different ways to tackle these write collisions. We could run a global sort, use atomic operations on every thread, coordinate at the warp level, or even skip the packing step entirely. Every option makes a drastically different tradeoff between moving data, syncing threads, and keeping the downstream math fast. The best choice ultimately depends on the specific workload numbers and the underlying GPU architecture. Exploring this landscape is what this project is all about.

Resources

  • Hardware: GHC cluster NVIDIA GPUs. PSC machines if multi GPU access is securely available.
  • Software: CUDA C++, CUB library, cuBLAS. NVIDIA Nsight Compute and Nsight Systems for deep profiling.
  • Starting point: All core kernel implementations will be built entirely from scratch. We will study the following open source implementations for design reference:
    • ScatterMoE scatter gather approach that entirely avoids explicit packing
    • MegaBlocks block sparse GEMM reformulation of expert computation
    • DeepEP high performance communication library for expert parallelism
    • SGLang / vLLM production MoE routing kernels using sort based dispatch algorithms

Goals and Deliverables

Plan to achieve
  • A solid sequential CPU baseline and a basic parallel GPU baseline for the core token packing step
  • Several parallel strategies taking fundamentally different approaches to handling memory, collisions, and synchronization
  • Performance benchmarking across a large variety of realistic MoE sizing configurations
  • An end to end single GPU layer benchmark completely covering routing, packing, and expert computation
  • A detailed analysis of tradeoffs showing precisely when and why each strategy performs the best
Hope to achieve
  • Distributed dispatch using NCCL alongside clean pipeline overlap via CUDA streams
  • A highly parallel CPU implementation utilizing OpenMP and MPI for complete cross platform comparison
  • A heavily fused single kernel routing implementation to eliminate all intermediate memory materialization steps
If things go slowly
  • Focus on deeply optimizing two main strategies instead of branching out into three or more
  • Reduce the entire parameter testing sweep and potentially drop the full layer benchmark portion

Platform Choice

NVIDIA GPU clusters and modern CPU environments.
